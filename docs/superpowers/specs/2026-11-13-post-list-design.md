# 게시글 목록 페이지 설계

## 의도

헤더의 유일한 메뉴 "게시글"에서 들어가는, 공개 게시글을 최신순으로 훑어보는 담백한 목록.
Medium 목록을 참고하되 화면 전체를 차지하지 않고, 글마다 **썸네일 + 제목 + 설명**만 눈에 들어오게 한다.
이 목록을 먼저 만들고, 이후 게시 기능을 다시 손본다.

## 목표

- `/posts` 에서 공개 글(`visibility = 'public'`)을 처음 게시한 시각 최신순(`published_at desc, id desc`)으로 한 줄씩 나열
- 한 줄: 왼쪽 썸네일, 오른쪽 제목(굵게) + 설명(내용 일부, 최대 2~3줄)
- 썸네일은 본문의 첫 번째 이미지, 없으면 기본 썸네일
- 번호 페이지네이션, 한 페이지 30개
- 헤더(PC)와 모바일 메뉴의 "게시글"이 `/posts` 로 이동
- 모바일 대응

## 하지 않을 것

- 작성자, 작성일 등 그 밖의 정보 표시
- 검색, 필터, 정렬 선택, 사이드 메뉴, 인기 글
- 페이지 상단의 제목·설명 문구 (화면에 보이는 것은 목록뿐, 접근성용 숨김 h1 만 유지)
- 무한 스크롤 (번호 페이지네이션으로 교체)
- DB 스키마 변경

## 접근 방식

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| **1. 조회 때 DB 에서 첫 이미지 주소만 뽑기 (선택)** | 마이그레이션 없음, 다시 게시하면 바로 반영, 본문 전체를 앱으로 가져오지 않음 | 조회마다 30개 본문을 DB 안에서 훑음 (지금 규모에서 문제 없음) |
| 2. 게시 때 썸네일 주소 컬럼에 저장 | 조회가 가장 가벼움 | 마이그레이션(운영 적용은 사용자), 게시·다시 게시 수정 필요 |
| 3. 본문 전체를 가져와 서버 코드에서 찾기 | 코드 단순, 테스트 쉬움 | 매번 30개 본문 전체 전송, 글이 길수록 무거움 |

사용자가 1번을 골랐다. 글이 많아지면 2번으로 옮기기 쉽다.

- 첫 이미지: `jsonb_path_query_first(content, 'strict $.**?(@.type == "image").attrs.src') #>> '{}'`
  (인용구 등 안쪽 이미지까지 본문 순서대로 찾는 것을 운영 DB 에서 확인함)
- 본문 이미지 주소는 게시할 때 공개 버킷 주소로 정리되어 있어 그대로 `<img>` 로 씀 (상세 본문과 같은 방식)
- 페이지네이션은 번호로 바로 이동해야 하므로 쪽 번호(offset) 조회 + 전체 개수(count). 기존 커서 기반 피드 조회는 제거

## 정한 동작

- 주소: 1쪽은 `/posts`, 그 밖은 `/posts?page=N`
- `page` 가 양의 정수가 아니면 1쪽으로 봄, 마지막 쪽보다 크면 404 (글이 하나도 없을 때는 빈 목록 문구)
- 줄 전체가 게시글 상세(`getPostPath`) 링크
- 글이 없으면 기존 문구 "아직 게시된 글이 없습니다"
- 페이지네이션: 이전/다음 화살표 + 번호, 첫·마지막 쪽과 현재 쪽 주변을 보여주고 사이는 `…`, 현재 쪽은 `aria-current="page"`, 1쪽뿐이면 숨김
- 헤더 "게시글": `/posts` 링크, 게시글 화면에서는 진한 글자색으로 현재 위치 표시

## 빌더에게 맡기는 것 (Claude 판단)

- 목록 폭: PC 가운데 최대 680px, 모바일 좌우 여백 20px, 줄 사이는 얇은 구분선 (카드 테두리 없음)
- 썸네일 크기: PC 160×107(3:2), 모바일 88×88, 둥근 모서리, `object-cover`
- 제목 최대 2줄, 설명 PC 3줄·모바일 2줄 말줄임
- 기본 썸네일: 연한 브랜드 배경 위 lucide `file-text` 아이콘 (정적 SVG)
- 페이지 번호 주변 개수: PC 현재 ±2, 모바일 ±1
- 화면 확인: 운영 DB 에 게시글이 0개라 빈 목록은 실제로, 목록·페이지네이션은 커밋하지 않는 임시 데이터로 확인
- 쓰지 않게 되는 무한 스크롤 피드 코드(`post-feed`, `post-card`, `loadPostFeed`, 피드 커서)는 삭제
