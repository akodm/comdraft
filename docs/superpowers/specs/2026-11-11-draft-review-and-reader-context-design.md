# 독자 기준 초안 작성과 검토·고쳐 쓰기 설계

- 작성일: 2026-11-11
- 상태: 브레인스토밍 합의 완료, 구현 전
- 대상: comdraft-lambda (프롬프트, 기획 스키마, 검토·고쳐 쓰기 단계, 예상량) + comdraft (진행 단계 이름)
- 앞선 설계: `2026-11-11-blank-fill-and-prompt-design.md` (글의 목소리·흐름·빈칸 상한, 빈칸 채우기)

## 1. 배경과 목적

앞선 개선 뒤 실제 초안을 써 보니 글 자체는 나아졌지만 아래 문제가 남았다.

1. **코드를 아는 독자처럼 쓴다.** 함수 이름 같은 내부 식별자가 설명 없이 튀어나온다. 분석 단계 규칙이 "함수 이름, 파일 경로는 입력 그대로 옮긴다"뿐이라 사실 문장이 코드 수준으로 정리되고, 작성 단계에는 "독자는 이 저장소를 본 적이 없다"는 기준이 없다.
2. **요청 문구를 어떻게든 섞는다.** 기획은 요청을 "가장 중요한 기준"으로 받고, 분석은 요청(`R`)을 근거로 사실을 만들 수 있어 요청 문장이 사실 목록에 들어간 뒤 그대로 글에 옮겨진다. 요청의 '방향 안내'와 '글감' 역할이 섞여 있다. 빈칸 다듬기도 "답을 사실로 삼아"라서 맥락에 안 맞는 답까지 넣으려 한다.
3. **참고 링크가 참고란에만 남는다.** 기획은 링크 본문 앞 300자만 보고, 분석 규칙은 "링크는 그 문서가 설명하는 내용의 근거로만"이라 코드와 문서를 잇는 사실이 만들어지지 않는다. 그래서 라이브러리 공식 문서대로 한 설정이 글쓴이만의 방식처럼 서술된다.
4. **검토 단계가 없다.** 작성 결과는 자리표시자 확인과 금지 요소 제거 같은 기계적 검사만 거친다.

목표:

1. 독자가 이 저장소·코드·요청을 모른다는 기준으로 모든 단계를 쓴다.
2. 요청과 빈칸 답은 안내와 글감으로 나눠, 맥락에 맞는 부분만 글에 녹인다.
3. 참고 링크의 역할을 판단해 코드·요청과 엮는다.
4. 작성 뒤 검토하고, 문제가 있을 때만 고쳐 쓴다.

## 2. 핵심 결정

| 주제 | 결정 |
|---|---|
| 검토 방식 | 검토(구조화된 문제 목록) → 문제가 있을 때만 고쳐 쓰기. 문제 없으면 호출 +1, 있으면 +2 |
| 링크 역할 | 기획 단계 모델이 링크 본문을 읽고 판단. 화면·DB 변경 없음 |
| 실패 처리 | 검토·고쳐 쓰기는 개선 단계라 실패, 형식 오류, 시간 부족이면 원래 초안을 저장. 작업은 실패시키지 않음 |
| 조립 위치 | 작성은 자리표시자 초안까지만. 조립(코드·링크·빈칸 넣기)은 마지막에 한 번 |
| 진행 단계 | 3단계 유지. 3단계 이름만 "작성" → "작성·검토" |
| 빈칸 다듬기 | 검토 없이 프롬프트 변경만 |
| 범위 밖 | 검토 결과 DB 기록, 링크를 가져오지 못한 사실의 화면 안내(시안 필요) |

## 3. 독자 기준 (모든 단계 공통 규칙)

ko/en 프롬프트에 공통 규칙 `READER_RULE` 을 추가하고 기획·분석·작성·검토·고쳐 쓰기·빈칸 채우기 system 에 넣는다. `voiceRuleMarker` 처럼 테스트용 표식 `readerRuleMarker` 를 둔다.

내용:

- 독자는 이 저장소, 코드, 요청 문구, 커밋 이력을 본 적 없는 개발자다. 글만 읽고 이해할 수 있어야 한다.
- 프로젝트 안에서만 쓰는 이름(함수, 변수, 타입, 파일 경로, 내부 모듈)은 본문에 그대로 꺼내지 않고 하는 일로 풀어 쓴다.
  - 예: "`createSafeLookup` 을 추가했다" 대신 "DNS 조회 결과가 공인 주소인지 확인하는 함수를 추가했다".
- 이름이 꼭 필요하면(코드 조각 바로 앞뒤 설명, 여러 번 가리켜야 하는 대상) 처음 나올 때 무엇인지 함께 설명한다.
- 라이브러리의 공개 API, 설정 키, CLI 명령어, 표준 용어는 독자가 문서에서 찾을 수 있으므로 이름 그대로 쓸 수 있다.

단계별 적용:

- **분석**: 사실 문장(`text`)과 코드의 볼 점(`point`)을 이 기준으로 쓴다. 식별자는 근거 번호로 확인할 수 있으니 문장에는 필요할 때만 넣는다. 기존 "이름·숫자는 입력 그대로 옮긴다" 규칙은 이름을 쓸 때 철자를 바꾸지 말라는 뜻으로 유지한다.
- **작성**: 기존 "일반 지식은 입력에 나온 용어의 개념을 짧게 설명할 때만" 규칙에 더해, 내부 이름을 역할로 풀어 쓰는 것은 새 사실을 만드는 일이 아님을 명시한다(사실과 코드에서 보이는 역할만 쓴다).

## 4. 요청과 답의 역할

### 4.1 요청 문구

- 요청은 글의 초점, 다룰 범위, 강조할 점, 글쓴이가 알려 준 배경을 정하는 **안내**다. 글에 옮겨 적을 문장이 아니다.
- **기획**: 요청이 초점과 목차를 정한다는 규칙은 유지하되, 요청의 문장 구성이나 표현을 절 제목·목적에 그대로 옮기지 않는다.
- **분석**: 요청(`R`)을 근거로 사실을 만드는 경우는 두 조건을 모두 갖출 때뿐이다.
  1. 글쓴이가 밝힌 경험이나 사실(계기, 결과, 수치, 프로젝트 설명)이다.
  2. 글 주제와 이 절의 목적에 맞는다.
- "~하게 써 줘" 같은 지시, 형식·분량 요구, 글 주제와 맞지 않는 내용은 사실로 만들지 않는다.
- 사실 문장은 요청의 표현을 베끼지 않고 독자가 읽을 말로 다시 쓴다.

### 4.2 빈칸 답 (빈칸 다듬기)

- 기존 "답을 사실로 삼아" 규칙을 바꾼다: 답 중 이 빈칸의 질문과 앞뒤 흐름에 맞는 부분만 골라 다듬는다. 맞지 않는 내용(다른 절의 이야기, 지시, 잡담)은 버린다.
- 답에 없는 내용을 더하지 않는다는 규칙은 그대로다.
- 답 전체가 맞지 않아도 질문에 가장 가까운 부분으로 짧게 쓴다(빈 결과는 지금처럼 실패로 처리됨).

## 5. 참고 링크

### 5.1 기획: 링크 역할 판단

- `LINK_PREVIEW_CHARS` 를 300 → **1,500** 으로 늘린다 (기획 단계 링크 미리보기).
- `PlanSchema` 에 `linkRoles` 를 추가한다:
  - `id`: 링크 번호 (L1 …)
  - `role`: `docs` (사용한 도구·라이브러리·서비스의 공식 문서나 가이드) / `article` (다른 사람의 글, 사례, 튜토리얼) / `discussion` (이슈, 토론, Q&A) / `other`
  - `relation`: 이 작업의 어느 부분과 어떻게 이어지는지 한 문장 (예: "번역 메시지 추출 설정이 이 문서의 설치 절차를 따른다"). 결과 언어로 120자 이내.
- `validatePlan`:
  - 입력에 없는 번호와 중복 번호는 버린다 (먼저 나온 것을 남김).
  - 입력 링크 중 `linkRoles` 에 없는 것은 `{ role: 'other', relation: '' }` 로 채운다. 결과는 입력 링크 순서다.
  - `relation` 은 120자로 자른다.
- 기획 프롬프트: 링크마다 역할과 관계를 정하는 규칙을 더한다. 관계는 링크 본문과 커밋 메시지·hunk 줄로 확인되는 것만 쓰고, 이어지는 부분이 없으면 비워 둔다.

### 5.2 분석: 코드와 문서 잇기

- 분석 입력의 `<link>` 에 `role`, `relation` 속성을 붙인다.
- 규칙 추가:
  - 코드 변경이 링크 문서(`docs`)의 절차, 권장 방식, API 사용법을 따른 것으로 보이면 그 사실을 hunk 와 링크를 **함께** 근거로 적는다 (예: "번역 메시지 추출 설정을 Lingui 공식 문서의 설정 절차대로 추가했다").
  - 문서와 다르게 한 점이 코드에서 보이면 그것도 사실로 적는다. 왜 다르게 했는지는 근거가 없으면 빈칸 규칙에 맡긴다.
  - 문서 내용은 이 작업을 이해하는 데 필요한 만큼만 사실로 옮긴다. 문서를 요약하는 사실을 늘어놓지 않는다.
- 기존 "링크의 방법이 적용됐다고 쓰려면 커밋이나 hunk 근거가 함께 있어야 한다"는 유지한다.

### 5.3 작성·검토·고쳐 쓰기

- 작성 입력의 `<links>` 항목에 `role`, `relation` 을 붙인다.
- 규칙 추가:
  - 공식 문서를 따른 작업은 "문서가 안내하는 방식을 따랐다"는 맥락을 밝히고, 그 문장에 `{{link:L…}}` 를 넣는다. 글쓴이가 혼자 고안한 방식처럼 쓰지 않는다.
  - 다른 글(`article`)이나 토론(`discussion`)을 참고했다면 무엇을 참고했는지 그 내용이 나오는 곳에서 밝힌다.
  - 문서 내용은 이 작업에 필요한 만큼만 짧게 쓴다.

## 6. 검토와 고쳐 쓰기

### 6.1 흐름

```
준비 → (예상량 검사) → 기획 → 분석 → 작성 → 검토 → (문제가 있으면) 고쳐 쓰기 → 조립 → 저장
```

- `Pipeline` 에 `review(input, written) => Promise<string>` 단계를 더한다.
  - `write` 는 자리표시자가 있는 Markdown 초안과 재료를 돌려준다 (`Written`: `Analyzed` + `draft`). 지금 `write` 안에서 하던 `assemble` 은 하지 않는다.
  - `review` 는 검토·고쳐 쓰기를 거친 초안(또는 원래 초안)을 `assemble` 해 최종 Markdown 을 돌려준다.
- `run-job` 은 `write` 다음 `review` 를 부른다. 새 `advance` 는 없다: 기록된 단계는 분석 완료(2)에 머물고, 화면은 지금처럼 3단계("작성·검토")를 진행 중으로 보여 주다가 완료 때 3이 된다. `review` 앞에 `ensureTime` 을 부르지 않는다 (시간 부족은 `review` 가 건너뛰기로 처리).
- `placeholder-pipeline.ts` 도 새 단계에 맞춘다 (초안을 그대로 돌려줌).
- `ClaudePipelineDependencies` 에 `remainingTimeMs: () => number` 와 `reportError?: (error: unknown) => void` 를 더한다 (handler 에서 넘김).

### 6.2 검토 단계

- `llm.parse`, effort `low`, maxTokens **4,000**.
- 입력:
  - 요청 문구 (`<request>`) — 그대로 베꼈는지 보는 용도
  - 글 재료 (`renderOutline` 과 같음: 제목, 요지, 절마다 사실·코드·빈칸)
  - 참고 링크 (번호, 제목, 역할, 관계)
  - 자리표시자 형태의 초안 (`<draft>`)
- 출력 `ReviewSchema`:
  - `issues`: 최대 **8**개, 중요한 것부터
    - `kind`: `unknown_term` | `request_echo` | `link_context` | `unsupported` | `voice` | `flow`
    - `quote`: 초안에서 고칠 부분을 글자 그대로 옮긴 것 (**200**자 이내)
    - `fix`: 어떻게 고칠지 한 문장 (**150**자 이내)
- kind 뜻:
  - `unknown_term`: 설명 없이 나온 내부 이름 (3절)
  - `request_echo`: 요청 문장을 그대로 옮기거나, 글 맥락에 맞지 않는 요청 내용을 넣음 (4.1)
  - `link_context`: 문서를 따른 작업을 독자적인 방식처럼 씀, 또는 링크가 참고란에만 있고 본문 맥락이 없음 (5.3)
  - `unsupported`: 재료(사실, 코드의 볼 점, 빈칸)에 없는 사실·수치·원인·효과
  - `voice`: 답변체, 보고서체, 출처 문장 (기존 목소리 규칙)
  - `flow`: 절 사이 연결이 끊김, 같은 말 반복, 도입·마무리 규칙 위반
- 검토 규칙: 확실한 문제만 적는다. 문체 취향이나 사소한 표현은 적지 않는다. 자리표시자(`{{…}}`)는 지적 대상이 아니다. 문제가 없으면 빈 목록을 낸다.
- 시스템 검증 (`validateReview`):
  - `quote` 가 초안에 없는 항목은 버린다. 비교는 양쪽 공백 연속을 하나로 줄인 뒤 부분 문자열로 한다.
  - 같은 `quote` 의 중복은 먼저 나온 것만 남긴다.
  - `quote` 가 자리표시자만으로 이뤄진 항목은 버린다.
  - 8개를 넘으면 자른다.
- 남은 항목이 없으면 고쳐 쓰기 없이 원래 초안을 쓴다.

### 6.3 고쳐 쓰기 단계

- `llm.write`, effort `medium`, maxTokens **16,000** (작성 단계와 같음).
- system: 작성 단계의 근거 범위·자리표시자·Markdown·분량 규칙을 그대로 쓰고, 고쳐 쓰기 규칙을 더한다:
  - 목록의 문제만 고치고, 문제가 없는 문장과 절 구성은 그대로 둔다.
  - 고치면서 새 사실을 더하지 않는다. 재료 범위 안에서 풀어 쓰거나 지운다.
  - 초안의 자리표시자는 모두 그대로 둔다. `{{link:…}}` 는 `link_context` 를 고칠 때 재료의 링크 번호로 더할 수 있다.
  - 응답은 고친 초안 전체 Markdown 만 쓴다.
- 입력: 글 재료, 참고 링크(역할·관계 포함), 초안, 문제 목록 (`<issue kind>` 에 `<quote>`, `<fix>`).
- 시스템 검증 (`acceptRevision`) — 하나라도 어기면 원래 초안을 쓴다:
  - 앞뒤 공백을 뺀 첫 줄이 `# ` 로 시작한다.
  - 초안에 있던 `{{code:…}}` 와 `{{ask:…}}` 가 각각 같은 횟수로 남아 있고, 새로 생긴 code·ask 번호가 없다.
  - `{{link:…}}` 번호는 모두 입력 링크에 있다.
  - 고친 본문이 비어 있지 않다.
- 응답을 감싼 바깥 코드 펜스는 검증 전에 푼다. `assemble.ts` 의 `unwrapOuterFence` 를 내보내 검토·고쳐 쓰기 모듈이 함께 쓴다 (작성 초안도 검토에 넘기기 전에 같은 함수로 푼다).

### 6.4 시간과 실패

- 상수 (`limits.ts` 또는 `llm.ts`):
  - `REVIEW_MIN_REMAINING_MS = 60_000`: 이보다 적게 남았으면 검토를 건너뛴다.
  - `REVISE_MIN_REMAINING_MS = 90_000`: 이보다 적게 남았으면 고쳐 쓰기를 건너뛴다 (`LLM_TIMEOUT_MS` 75초 + `SAFETY_MARGIN_MS` 15초).
- 검토·고쳐 쓰기 호출에서 나온 오류(`llm_failed`, `timeout`, 스키마 오류)는 `reportError` 로 남기고(사유 코드만, 내용 없음) 원래 초안으로 넘어간다. 작업은 실패하지 않는다.
- 다만 다른 곳에서 작업이 끝났는지 여부는 지금처럼 `complete` 결과로 판단한다 (변경 없음).
- 사용량은 결과를 버려도 호출마다 기록한다 (기존 `onUsage`).

### 6.5 예상량

`estimateJobTokens` 에 두 단계를 더한다 (모두 실행된다고 보고 넉넉하게):

- `SystemTokens` 에 `review`, `revise` 추가 (각 system 프롬프트 토큰).
- 새 상수:
  - `ESTIMATE_OUTLINE_CODE = 4_000`: 글 재료에 들어가는 코드 원문 여유분
  - `ESTIMATE_REVIEW_OUTPUT = 2_000`: 검토 출력
- 더하는 양:
  - 검토 입력: `requestTokens` + 재료(`ESTIMATE_ANALYSIS_OUTPUT` + `ESTIMATE_OUTLINE_CODE`) + 초안(`ESTIMATE_WRITE_OUTPUT[length]`)
  - 검토 출력: `ESTIMATE_REVIEW_OUTPUT`
  - 고쳐 쓰기 입력: 재료(`ESTIMATE_ANALYSIS_OUTPUT` + `ESTIMATE_OUTLINE_CODE`) + 초안(`ESTIMATE_WRITE_OUTPUT[length]`) + `ESTIMATE_REVIEW_OUTPUT`
  - 고쳐 쓰기 출력: `ESTIMATE_WRITE_OUTPUT[length]`
- 작성 단계 입력의 코드 원문도 지금 빠져 있으므로 `ESTIMATE_OUTLINE_CODE` 를 한 번 더 더한다.
- 실제 사용량은 대략 한 건당 30~50% 늘고, 고쳐 쓰기가 없으면 10~15% 늘 것으로 본다.

## 8. 배포

- 마이그레이션 없음. Lambda 와 comdraft 는 서로 독립적이라 순서 제약이 없다 (comdraft 는 단계 이름만 바뀜).
- Lambda 는 `comdraft-main-iam` 프로필로 terraform plan 을 보여 드린 뒤 승인 받아 apply 한다.
- 배포 전 로컬에서 실제 Claude 로 커밋 하나(예: 번역 라이브러리 설정 커밋 + 그 문서 링크)를 돌려 전후 초안을 비교한다. 사용량이 들므로 실행 전 확인을 받는다.

## 9. 테스트

Lambda 단위 테스트:

- `validatePlan`: 모르는 링크 번호·중복 제거, 빠진 링크는 `other`, 순서는 입력 링크 순, `relation` 120자 자름
- `validateReview`: 초안에 없는 `quote` 버림, 공백 차이는 같은 것으로 봄, 중복·자리표시자만 있는 항목 버림, 8개 상한
- `acceptRevision`: 제목 없음, code·ask 누락·중복·새 번호, 모르는 link 번호, 빈 본문이면 거절. link 추가는 허용
- 파이프라인 `review`:
  - 문제 없음 → 고쳐 쓰기 호출 없이 원래 초안 조립
  - 문제 있음 → 고쳐 쓴 초안 조립
  - 검토 실패 / 고쳐 쓰기 실패 / 고쳐 쓰기 검증 실패 → 원래 초안, `reportError` 호출
  - 남은 시간 60초 미만 → 검토 호출 없음, 90초 미만 → 고쳐 쓰기 호출 없음
  - 검토·고쳐 쓰기 사용량이 `onUsage` 로 기록됨
- `run-job`: 작성 뒤 `review` 결과가 저장되고, 단계는 3을 넘지 않음
- `estimateJobTokens`: 새 단계 항목이 더해짐
- 프롬프트: ko/en 이 같은 키를 갖고, `READER_RULE` 표식이 여섯 system 에 모두 있음, 기획 입력 미리보기가 1,500자
- 렌더링: 분석 입력 `<link>` 와 작성·검토·고쳐 쓰기 입력 링크에 `role`, `relation` 이 붙음

- 진행 표시 3단계 이름 (기존 테스트가 이름을 보면 갱신)
