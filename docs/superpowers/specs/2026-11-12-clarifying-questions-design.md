# 작성 전 되묻기 설계

- 작성일: 2026-11-12
- 상태: 브레인스토밍 합의 완료, 구현 전
- 대상: comdraft-lambda (기획 스키마·프롬프트, 작업 실행 흐름) + comdraft (작업 상태, 질문 카드 화면, 서버 액션, 마이그레이션)
- 앞선 설계: `2026-11-11-draft-review-and-reader-context-design.md` (독자 기준, 검토·고쳐 쓰기)

## 1. 배경과 목적

초안의 품질은 내부 프롬프트만큼 사용자가 보내는 요청에도 달려 있다. 커밋 메시지가 "update", "fix" 수준이고 요청마저 한 줄이면, AI 는 기본 옵션(말투·글 종류·길이)만 보고 글의 방향을 짐작해야 한다. 이때 나오는 초안은 방향이 틀리기 쉽고, 빈칸으로도 메울 수 없다. 빈칸은 세부 사실을 묻는 장치라 글 전체의 중심이 비어 있는 문제를 풀지 못한다.

목표:

1. 커밋 메시지·diff·요청·참고 링크로 **글의 흐름이나 맥락을 정할 수 없을 때만** 작성 전에 사용자에게 되묻는다.
2. 세부 사실은 묻지 않는다 (빈칸의 몫). 정보가 충분하면 지금처럼 바로 작성한다.
3. 답하는 부담을 줄인다. 대상 사용자는 요청을 한 줄로 넘긴 사람이다.

## 2. 핵심 결정

| 주제 | 결정 |
|---|---|
| 묻는 시점 | 작성 시작 후. Lambda 가 diff 까지 읽고 판단하며, 부족하면 작업을 멈추고 묻는다 |
| 판단 위치 | 기획 단계가 함께 판단 (기획 출력에 `clarify` 필드). 평소 요청은 Claude 호출이 늘지 않음 |
| 답변 형식 | 질문마다 diff 에 근거한 보기 2~3개 + 직접 입력 |
| 답이 없을 때 | 답할 때까지 기다림 (시간 초과 없음). 답하기 / 그냥 작성 / 취소 |
| 묻는 횟수 | 작업당 한 번. 재실행에서는 다시 판단하지 않음 |
| 답의 쓰임 | 기획·분석·작성·검토 프롬프트에 "작성자가 보탠 맥락"으로. 작성자의 말이라 요청처럼 사실로 써도 됨 |
| 범위 밖 | 빈칸 채우기 작업(kind='fill')의 되묻기, 여러 번 주고받는 대화, 질문 기록의 통계 화면 |

## 3. 작업 상태와 흐름

### 3.1 상태와 저장

- `draft_prompt.status` 에 `awaiting_input` (답변 대기) 추가.
  - `lib/db/schema/draft.ts` 의 `DRAFT_PROMPT_STATUSES`, `draft_prompt_status_check` 제약에 추가.
  - 활성 작업 유일 인덱스 `draft_prompt_draft_active_unique` 의 조건을 `status in ('queued', 'running', 'awaiting_input')` 으로 바꾼다 (답변 대기 중에는 그 초안에 새 작성 요청을 받지 않음).
- 컬럼 `clarification jsonb` (null 이면 아직 묻지 않은 작업) 추가:

```ts
interface Clarification {
  reason: string;                       // 왜 묻는지 한 줄 (화면에 표시)
  questions: {
    id: string;                         // 'Q1' ...
    question: string;
    options: string[];                  // 0~3개 (0개면 직접 입력만)
  }[];
  // null: 답변 대기, 배열: 답함 (답한 질문만), 'skipped': 그냥 작성
  answers: { id: string; answer: string }[] | 'skipped' | null;
}
```

- 마이그레이션 파일은 `pnpm db:generate` 로 만들고, 운영 적용은 사용자가 한다 (임의로 `db:migrate` 하지 않음).
- `contract.ts` (양쪽 저장소 공용): `GenerationStatus` 에 `awaiting_input`, 오류 코드에 `cancelled` 추가.

### 3.2 흐름

1. **Lambda 첫 실행**: 준비 → 예상량 예약 → 기획. 기획 결과의 `clarify.needed` 가 참이고 이 작업의 `clarification` 이 null 이면:
   - 질문을 `clarification` 에 저장하고 `awaiting_input` 으로 바꾼다 (`running` 인 작업만, 단계는 0 유지).
   - 예약한 예상량(`estimated_tokens`)을 비운다. 사용량은 실제로 쓴 토큰(기획 1회)만 남는다.
   - Realtime 신호를 보내고 Lambda 를 끝낸다 (`RunJobOutcome` 에 `'awaiting_input'` 추가).
2. **화면**: 질문 카드에서 답하기 / 그냥 작성 / 취소.
   - 답하기·그냥 작성: 서버 액션이 `answers` 를 저장하고 `awaiting_input` → `queued` (내 작업이고 답변 대기인 작업만), `step = 0`, `started_at = now()` (queued 시간 초과를 재대기 시각부터 재기 위함), 같은 jobId 로 Lambda 를 다시 호출한다.
   - 취소: `awaiting_input` → `failed`, 오류 코드 `cancelled`.
   - 작성기 호출에 실패하면 지금처럼 `runner_unavailable` 로 실패 처리.
3. **Lambda 재실행**: `clarification` 이 있으므로 판단하지 않는다 (프롬프트에 판단하지 말라고 넣고, 코드에서도 `clarify` 를 무시). 준비부터 다시 하고 예상량을 다시 예약한 뒤, 답을 넣어 기획부터 진행한다.
   - 커밋 상세는 다시 조회한다 (GitHub 조회는 싸고, 준비물을 저장하지 않기 위함).
   - 제목 수준이 빠져 기획을 다시 하는 경우(replan)에도 판단하지 않는다.

### 3.3 사용량·잠금·시간

- 사용량: 주간 사용량 계산에서 `awaiting_input` 작업은 `used_tokens` 만 센다 (진행 중 작업처럼 예상량으로 세지 않음).
- 잠금: `awaiting_input` 은 `isJobLocking` 대상 (진행 중처럼 편집기를 잠금).
- 시간 초과: `awaiting_input` 은 `isJobStale` 대상이 아니다. 재실행 때 `started_at` 을 새로 기록하므로 7분 제한은 그때부터 잰다. queued 시간 초과는 `coalesce(started_at, created_at)` 기준으로 본다.
- 시간당 요청 제한: 재실행(답하기·그냥 작성)은 새 요청으로 세지 않는다.

## 4. 화면

- 위치: 입력창 아래 진행 표시(`GenerationProgress`) 자리. 작업이 `awaiting_input` 이면 진행 단계 대신 질문 카드를 보여 준다.
- 카드 머리: "글의 방향을 정하려면 조금 더 알려 주세요" + `reason` 한 줄.
- 질문 1~3개: 질문마다 보기 라디오 + 마지막 "직접 입력" (고르면 입력칸이 열림, 500자 이하). 일부만 답해도 된다.
- 버튼:
  - **답하고 작성** (주 버튼, 하나 이상 답해야 활성)
  - **그냥 작성** (답 없이 진행)
  - **취소**
- 누르면 진행 단계 표시로 돌아가 "구분"부터 진행한다.
- 떠났다 돌아오면: 그 초안을 열 때 작업 조회로 같은 카드를 다시 보여 준다. 초안 목록에는 답변 대기 중인 초안에 "답변 대기" 표시 (목록 조회에 활성 작업 상태를 함께 읽음).
- Realtime 구조는 그대로 (신호를 받으면 상태 조회).
- 문구는 Lingui ko/en. 모바일에서는 보기와 버튼을 세로로 쌓는다. 테일윈드 v4, 아이콘은 lucide.

## 5. 판단 기준과 프롬프트

### 5.1 묻는 조건 (모두 해당할 때만)

1. **글의 중심**(무엇에 대한 글인지) 또는 **작업의 동기·겪은 문제**를 커밋 메시지·diff·요청·참고 링크 어디서도 알 수 없다.
2. 그 공백 때문에 기획이 서로 전혀 다른 글로 갈린다 (예: 설정 소개 글 vs 문제 해결기).

묻지 않는 것: 세부 사실(어떤 값, 몇 번 시도, 어느 페이지 — 빈칸의 몫), 소감, diff 에서 추론할 수 있는 것. 요청을 충분히 쓴 경우는 사실상 묻지 않는다.

### 5.2 질문과 보기

- 질문은 최대 3개, 서로 다른 면: 동기·문제 / 독자에게 남길 것(글의 중심) / 여러 주제가 섞였을 때 무엇을 중심으로 할지.
- 보기는 2~3개, 짧은 한 문장. 커밋 메시지와 diff 에 드러난 것으로만 만든다 (드러나지 않은 사실을 지어내지 않음).
- 질문·보기는 작업 로케일로 쓴다.

### 5.3 출력 형식과 검증

- `PlanSchema` 맨 앞에 `clarify: { needed: boolean, reason: string, questions: { question: string, options: string[] }[] }` 추가 (모델이 목차를 짜기 전에 먼저 판단하도록 앞에 둠).
- 검증 코드가 보정:
  - `needed` 인데 질문이 0개면 묻지 않는 것으로 본다.
  - 질문 4개째부터, 보기 4개째부터, 빈 문장은 버린다.
  - 보기가 2개 미만이면 보기를 비우고 직접 입력만 남긴다.
  - 질문 id 는 코드가 `Q1`, `Q2` … 로 붙인다.
- 판단 기준은 ko/en 기획 system 프롬프트에 추가한다. 재실행 때는 user 프롬프트에 "이미 작성자에게 물었으니 clarify.needed 는 false" 를 넣는다.

### 5.4 답의 전달

- 기획·분석·작성·검토(고쳐 쓰기 포함) user 프롬프트의 요청 옆에 "작성자가 보탠 맥락" 블록으로 넣는다 (질문 + 답 쌍). 그냥 작성이면 블록을 넣지 않는다.
- 보기를 고른 답은 그 보기 문장을 그대로 넣는다.
- 작성자가 직접 고르거나 쓴 말이므로 요청과 같은 수준의 근거로 쓴다 (분석 단계 사실의 근거로 `R` 처럼 인용 가능).
- 예상량 계산(`estimateJobTokens`)에 답의 길이를 포함한다.

## 6. 검증

### 6.1 Lambda 단위 테스트

- `clarify` 검증: 질문 0개, 4개 이상, 빈 보기, 보기 1개.
- 멈춤 경로: `awaiting_input` 전환, 질문 저장, 예상량 비움, 단계 미진행, 결과 `'awaiting_input'`.
- 재실행 경로: 다시 묻지 않음, 답이 기획·분석·작성·검토 프롬프트에 들어감, 그냥 작성이면 답 없이 진행.
- replan 때 판단하지 않음.

### 6.2 Next.js 단위 테스트

- 작업 상태: 답변 대기는 잠금 대상이고 시간 초과 아님.
- 답변 검증: 질문 id, 500자 제한, 답하기는 하나 이상.
- 서버 액션: 내 작업이고 답변 대기인 작업만 `queued` 로, 취소는 `cancelled`, 시간당 요청 제한에 세지 않음.
- 사용량: 답변 대기 작업은 `used_tokens` 만 셈.

### 6.3 품질 비교 (실제 Claude, 비교 도구)

- **T10**: T1 과 같은 커밋, 메시지는 "update" / "fix" 수준, 요청은 "블로그 글 써줘" 한 줄 → 물어야 하고, 질문·보기가 diff 에 근거해야 한다.
- **T11**: 메시지는 부실하지만 diff 만으로 주제가 분명한 경우 → 묻지 않아야 한다.
- **T1~T9**: 하나도 묻지 않아야 한다 (필요 없는 질문 회귀 확인).
- **T10 + 답**: 답을 넣고 재실행한 결과가 답의 방향을 따르는지.

### 6.4 화면 (로컬)

- 가짜 작성기(`fake-runner`)에 질문을 돌려주는 경우를 추가해 Lambda 없이 확인: 카드 표시, 답하기·그냥 작성·취소, 떠났다 돌아왔을 때, 모바일 폭.

## 7. 배포 순서

옛 코드가 모르는 상태를 먼저 만들지 않도록 아래 순서로 배포한다.

1. **마이그레이션**: `clarification` 컬럼, 상태 제약, 활성 작업 유일 인덱스. 운영 적용은 사용자.
2. **Next.js**: 답변 대기 상태와 재실행 처리. 이때까지 Lambda 는 묻지 않으므로 화면 변화 없음.
3. **Lambda**: 판단 켜기 (`contract.ts` 동기화). terraform plan 을 보여 주고 승인 후 apply.
